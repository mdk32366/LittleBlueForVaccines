# eval.py mechanism behind the out-S exit 3 (read from /workspace/littleblue-eval-v0.5/eval.py, sha256 429751f6b8e05f8cba63ca1e858f883ef71022d8cdb2aee736200d71b7ffdb25; evalcore.py 2d1d2f9b…ba75)

1. **What `--peak_limit` measures.** `after_batch` (L308–L311): `pk = torch.cuda.max_memory_allocated(); if pk > a.peak_limit: abort(3, …)`. That is the CUDA caching allocator's peak of bytes held by live tensors, not `max_memory_reserved` (the pool, which eval.py records only at the end of a complete run, L379, and in a PREFLIGHT file, L323). The peak counter is reset once per process, right after the model and adapter load (L264 `torch.cuda.reset_peak_memory_stats()`), and never per batch, so the value checked after batch k is the largest allocation since the load of this process.
2. **When it is checked.** In the generate loop (L366–L372): generate the batch (L367), write its rows and fsync (L368–L370), then `after_batch` (L371), then print the progress line (L372). An exit 3 therefore comes after the batch that tripped it is on disk, and that batch has no progress line. "after row 2920" (`after_batch` is passed the rows written in this session, L371) = 365 whole batches of 8 (batches 0–364, fewshot plan) when the session started at batch 0.
3. **Run identity.** `cfg` (L187–L191): schema, tag, mode, rows sha, manifest sha, run-manifest text, input shas (rows, eval.py, evalcore.py, fewshot), model path + every top-level model file sha, adapter path + manifest sha + file shas, `max_new_tokens`, `batch`, `kinds`, `limit`, `backend`, seed, decoding. A resume with any difference → exit 7, nothing written (L192–L194). Also exit 7 on library versions different from the first session (L228–L229), on a completed run (L145), unknown files in the out dir (L138–L140), a live lock (L99–L101) or a running status with a live pid (L149–L151). **Not** in cfg: `--peak_limit`, `--min_free`, `--pin_transformers`, `--expect_versions`, `--manifest` path. (`--pin_transformers` still has to equal the installed version, or exit 13, L235.)
4. **M2 fixed boundaries.** `plan_batches` (evalcore.py L115–L128): rows sorted by (`fs_prompt_tokens` in few-shot mode, id), cut into consecutive slices of `--batch`. The resume keeps every batch whose rows are all present (L350), drops partial batches (L351–L359), and generates the rest in order (L360). Changing `--batch` changes every boundary, and is refused by item 3.
5. **Resume of a stopped run.** Same line → state check (status `aborted`, no lock → allowed), lock taken, cfg equal, the new session appended (L336), whole batches kept, `batches_done_at_start` recorded (L361). The merged-config / greedy check runs again on the first generate of the new session (L298–L302) and the transformers pin check again before the load (L234–L242). The free-memory floor is checked again at start (L246).
6. **What a fresh process changes.** Everything held by the CUDA allocator belongs to the process; a new process starts with only the model (preflight peak 2,253,176,832) and resets the peak counter after the load.
